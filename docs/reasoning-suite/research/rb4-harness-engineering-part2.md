# Harness Engineering in Major SWE Benchmarks (2/3)

## 3. Continuous gold-solution CI

- **BigCodeBench embeds gold replay in every evaluation run**: the evaluator computes and prints a **"Groundtruth pass rate"** (expected 1.000) by default before scoring samples; `--check_gt_only` runs ONLY the gold check (usable in CI via the Docker image), `--no_gt` opts out (https://github.com/bigcode-project/bigcodebench/blob/main/ADVANCED_USAGE.md). Fully automated, at every evaluation — the strongest continuous-gold discipline among the big benchmarks.
- **SWE-bench's gold replay is on-demand, not CI**: `run_evaluation --predictions_path gold --run_id validate-gold` re-scores the reference patches; it is the standard reproduction step whenever an instance is challenged (issues https://github.com/SWE-bench/SWE-bench/issues/372, https://github.com/swe-bench/SWE-bench/issues/267, https://github.com/SWE-bench/SWE-bench/issues/484). The one-time 99.78%/100% validation happened at the Docker cutover; nothing re-runs golds automatically on dependency or harness changes — which is exactly how #484-class rot went unnoticed.
- **Terminal-Bench gates merges on the oracle**: every task ships `task.yaml` + `Dockerfile` + deterministic pytest `tests/` + a human-written **`solution.sh` oracle**; CI validates the oracle passes the tests, plus adversarial checks and LLM-based specification reviews; a dedicated CI check asserts the **Dockerfile contains neither tests nor the oracle** (anti-cheat); average **>3 person-hours per task** confirming specification-iff-state, solvability, and anti-triviality (https://github.com/harbor-framework/terminal-bench, https://arxiv.org/abs/2601.11868 — Appendix B: contributor checklist, check tools, debug tool, adversarial exploit agent, ABC assessment covering outcome validity / task validity / benchmark reporting).
- **METR treats golds as regression tests**: reference solutions are re-run whenever a task is revised "to make sure the score of the gold solution stays the same, or changes in the predicted way, if the revision is updating the scoring function"; QA additionally requires a NON-AUTHOR human attempting the task with only agent-available resources, and an agent (Claude 3.5 Sonnet) attempting each task **5 times with manual transcript review** (https://taskdev.metr.org/quality-assurance/, https://github.com/METR/task-standard).

## 4. Flakiness policy

- **SWE-bench Verified (construction-time filter, human)**: 93 developer-annotators, 1,699 sampled instances, each annotated by **3 separate annotators** (ensembled), rubric severities 0-3 per criterion — 0/1 minor, 2/3 discard. Result: **68.3% of SWE-bench filtered out** — 38.3% flagged underspecified, 61.1% flagged for unit tests that could unfairly reject valid solutions — plus explicit removal of instances failing "due to environment problems instead of the solution" (https://openai.com/index/introducing-swe-bench-verified/, detail mirror: https://github.com/irthomasthomas/undecidability/issues/933, https://epoch.ai/benchmarks/swe-bench-verified).
- **Rerun-N stability gates (automated, construction-time)**: SWE-rebench reruns each candidate instance's tests **3x and keeps it only if structured test outcomes are identical across runs** (https://arxiv.org/html/2602.23866); SWE-Bench++ builds and instantiates each Docker testbed **3x** and keeps only instances that initialize all three times (https://arxiv.org/html/2512.17419v1).
- **Published residual flake rates**: SWE-bench Docker harness 5/2,294 (0.22%) instances don't consistently resolve with gold. BigCodeBench acknowledges **~0.2% (Full) / ~0.6% (Hard) run-to-run score variance** with named causes — flaky tests, socket timeouts, missing random-state setup (https://github.com/bigcode-project/bigcodebench/blob/main/ADVANCED_USAGE.md, https://huggingface.co/blog/leaderboard-bigcodebench). LiveCodeBench: <0.5-point timeout-induced variation, ERRATA.md quarantine list.
- **Consumer-side quarantine**: researchers report on subsets excluding known-flaky-test problems rather than rerunning (e.g. https://github.com/ScalingIntelligence/swe-bench-lite-samples).
- **Notable absence**: no official SWE-bench leaderboard mandates N-run reporting per submission; flakiness is pushed to construction-time filtering rather than run-time replication (contrast Epoch's 16-run practice).

## 5. Dataset versioning and re-benching

- **SWE-bench versions by named subset, not semver**: full (2,294) -> Lite (300) -> **Verified (500, Aug 2024)**, each with a separate leaderboard; scores never migrate between them. Post-release brokenness is handled by SUPERSEDING (Verified replacing full/Lite as headline) rather than patching in place; instance-level challenges live as GitHub issues against the dataset (#267, #484).
- **End-of-life is also a versioning act**: OpenAI publicly deprecated Verified (saturation: SOTA moved only 74.9% -> 80.9% in 6 months; >=59.4% flawed tests in the audited hard subset; contamination from training on public repos) and moved reporting to SWE-bench Pro — old scores left standing but declared non-informative (https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/, https://x.com/OpenAIDevs/status/2026002219909427270, https://www.latent.space/p/swe-bench-dead).
- **BigCodeBench versions in place with changelogs**: `v0.1.1` fixed tasks 178, 760, 1005, 1006; v0.1.2-v0.1.4 fixed more; the evaluator + leaderboard pin the dataset version (https://huggingface.co/datasets/bigcode/bigcodebench/blob/main/README.md, https://github.com/bigcode-project/bigcodebench-annotation/releases).
- **LiveCodeBench versions by accretion**: `release_v1`-`v6` are strict supersets (400 -> 1,055 problems); old scores stay comparable because the leaderboard slices by problem-date window per model rather than freezing one set (https://livecodebench.github.io/leaderboard.html).
- **SWE-bench-Live re-versions monthly by design**, making contamination-driven re-benching a scheduled event instead of a crisis (https://github.com/microsoft/SWE-bench-Live/blob/main/README.md).
- **Third-party re-scoring as forced re-bench**: UTBoost's augmented tests flipped 18 (Lite) / 11 (Verified) leaderboard rankings — dataset fixes retroactively invalidate published orderings even when the harness never changed (https://arxiv.org/abs/2506.09289).
