## 3. OpenRouter beta batches
- create response shape (successful create, top-level, no `data` wrapper): `id`, `object`, `endpoint`, `model`, `completion_window`, `status`, `created_at`, `finalized_at`, `request_counts` (`total`/`completed`/`failed`), `usage`, `error`, `results`
- key order `{endpoint, model, requests}` accepted: yes
- model support is per-model, not universal: `openai/gpt-4o` (the model OpenRouter's own batch-quickstart docs give as a working example) and `openai/gpt-5-mini` were BOTH rejected identically at create time with `400 {"error":{"message":"Model '<id>' does not have a :batch endpoint.","code":400}}`. `google/gemini-3.8-flash` was accepted (`202`). The adapter must therefore treat "model has no batch endpoint" as a hard per-model 400, not something a retry or a different account fixes.
- results inline on `completed`: yes. The completed Gemini batch's GET response carried a populated top-level `results[]` array (`{ id, custom_id, response: { status_code, request_id, body }, error }` per item, `body` = a normal chat-completions response object); non-completed (`validating`/`in_progress`) responses carried `results: null`.
- batch-level `usage.cost`: observed `0.0000045` (1-item batch, 7 prompt + 1 completion tokens) and `0.425996625` (4096-item batch, 4096 prompt + 226379 completion tokens). `usage` is `null` until `completed`.
- Gemini 3.8 Flash `reasoning` param accepted: yes, form `{ reasoning: { effort: "low" } }` in the per-item body. Batch created (202) and completed normally; OpenRouter resolved the slug to a dated variant `google/gemini-3.8-flash-20260902` in every response.
- `created_after` list filter honoured: yes. The one `GET ?created_after=<10-min-ago ISO>` call in the run, issued moments after the Gemini batch completed, returned the Gemini batch itself, not an empty result (openrouter.log line 68): `{"object":"list","data":[{"id":"batch-1788696445-TdqrQ2S1uuUA5M4Z8Lep","object":"batch","endpoint":"/v1/chat/completions","model":"google/gemini-3.8-flash-20260902","completion_window":"24h","status":"completed","created_at":1788696445,"finalized_at":1788697036,"request_counts":{"total":1,"completed":1,"failed":0},"usage":{"prompt_tokens":7,"completion_tokens":1,"total_tokens":8,"cost":0.0000045,"is_byok":false},"results":null,"error":null}],"first_id":"batch-1788696445-TdqrQ2S1uuUA5M4Z8Lep","last_id":"batch-1788696445-TdqrQ2S1uuUA5M4Z8Lep","has_more":false}`. (An earlier draft of this finding misread this line as an empty result; it is not: `data` contains exactly the one batch created moments earlier, correctly filtered.)
- ceiling, items: NOT reached. Doubled 8 -> 4096 items (`google/gemini-3.8-flash`, 1-token bodies), every create returned `202`. See "Post-run polls (raw)" below for reviewable confirmation that the 4096-item and 2048-item batches both completed in full, not just got accepted.
- ceiling, bytes: NOT reached as a batch-API limit within the tested range, and the doubling loop's own break condition fired for an unrelated reason. 64 KiB through 4096 KiB single-item bodies (repeated `"x"` content) all returned `202` at create time. See "Post-run polls (raw)" below: 512/1024/2048 KiB all completed, but the 4096 KiB batch failed at processing on the target model's own context window, not a batch-endpoint size limit. The pre-flight token estimate behind that error looks like a generic ~4-chars/token heuristic (4,194,304 content chars / 4 ~= 1,048,576, close to the stated 1,048,576-token limit), while the actual completed batches' `usage.prompt_tokens` show a real ratio close to 8 chars/token for this repeated-character payload (e.g. 2,097,152 chars -> 262,144 tokens on the 2048 KiB batch, matching the 2048 KiB poll below). The subsequent 8192 KiB attempt never got far enough to test either limit: it was rejected at create time with `429 {"error":{"message":"Rate limit exceeded: entity-ratelimit. ","code":429,"metadata":{"headers":{"X-RateLimit-Limit":"16","X-RateLimit-Remaining":"0","X-RateLimit-Reset":...}}}}`, a batch-creation rate limit (16 per rolling window, observed after ~17-18 create calls in the run), unrelated to request size.
- initial adapter limits: `maxItems = 2048` (half of 4096, the largest item count that both accepted AND completed cleanly per the polls below); `maxBytes = 1 MiB` (half of ~2048 KiB / 2,097,152 bytes, the largest single-item body that both accepted AND completed, NOT half of the 4096 KiB value, since that one failed at processing on the target model's context window rather than surviving). Separately: cap outbound batch-creation calls to well under 16 per short window to avoid `entity-ratelimit` 429s. This is a rate limit, not a size/item ceiling, so Plan B needs its own backoff/pacing for it independent of `maxItems`/`maxBytes`.
