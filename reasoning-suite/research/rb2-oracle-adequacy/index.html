    Test-Oracle Adequacy in Execution-Based Code Benchmarks — Research Report¶

    1. EvalPlus (HumanEval+ / MBPP+) — the canonical case¶

    Paper: "Is Your Code Generated by ChatGPT Really Correct?" (NeurIPS 2023), https://arxiv.org/abs/2305.01210 ; NeurIPS PDF: https://proceedings.neurips.cc/paper_files/paper/2023/file/43e9d647ccd3e4b7b5baab53f0368686-Paper-Conference.pdf

    Amplification pipeline (Sec 2.1, fully automated): - LLM seed generation: ~30 ChatGPT-generated seed inputs per task from 3 prompts; each prompt = ground-truth implementation + sampled existing test inputs + instruction to produce "interesting" inputs (exploits LLM semantic understanding for inputs with complex validity constraints). - Type-aware mutation (Table 1) expands seeds: int/float x±1; bool random flip; str remove/repeat/replace substring with mutated version; List remove/repeat/insert/replace element; Tuple/Set convert to List, mutate, convert back; Dict remove pair, mutate value, insert mutated pair. An "ingredient mechanism" recycles data fragments seen in prior inputs. Budget: 1,000 extra inputs/task under a 1-hour compute budget. - Contracts (Sec 2.3): 83/164 HumanEval tasks got hand-written precondition assertions (e.g. assert n > 0) to filter generated inputs that trigger undefined behavior — the guard that keeps automated fuzzing from producing false failures in differential comparison. (Human, one-time.)

    Scale: HumanEval 9.6 avg tests/problem -> HumanEval+ 764.1 (80x, range 12-1,100). MBPP+ 3.1 -> 108.5 (35x) on a 399-problem subset hand-trimmed from the 427-problem MBPP-sanitized set (https://github.com/evalplus/evalplus/releases/tag/v0.2.0).

    Ground-truth cross-checking (Sec 3, human+automated): differential testing of amplified inputs against re-implemented references exposed 18/164 (11%) wrong ground truths in original HumanEval — 5 mishandled edge cases, 10 logic errors, 3 performance/timeout defects (e.g. validate_date #124 had an and/or precedence bug). All ground truths re-implemented and re-tested.

    Published false-pass effect: pass@1 drops up to 19.3% (greedy pass@1 up to 23.1%), pass@10 up to 24.9%, pass@100 up to 28.9%* across 26 models. GPT-4: 88.4% -> 76.2%. Rankings flip: WizardCoder-CodeLlama and Phind-CodeLlama overtake ChatGPT only on HumanEval+.

    Reduction to a minimal adequate set (Sec 2.2, automated): greedy set cover over three requirement classes — (a) branch coverage, (b) killed mutants (mutation testing over ground truth), (c) killed wrong LLM samples (leave-one-out across models' incorrect solutions). Result: HumanEval+-mini, 47x smaller (16.1 avg tests) with preserved detection power. Design note: mutation analysis is used INSIDE benchmark construction as the adequacy criterion.

    Determinism/timeouts (Appendix A): runtime cap max(200ms, 4 x ground-truth time); float comparison at absolute 1e-6 unless problem-annotated; exact-match oracle otherwise.

    Lifecycle: amplification + reduction at construction; contracts and ground-truth re-implementation are one-time human effort; scoring fully automated thereafter.

    2. LiveCodeBench¶

    Paper: https://arxiv.org/pdf/2403.07974 ; site https://livecodebench.github.io/ ; ICLR 2025 https://proceedings.iclr.cc/paper_files/paper/2025/file/94074dd5a072d28ff75a76dabed43767-Paper-Conference.pdf ; repo https://github.com/livecodebench/livecodebench

    Sources and tests (Sec 3.2, initial release): 511 problems (May 2023-May 2024): LeetCode 235, AtCoder 267, Codeforces 9. Avg 17.0 tests/problem (LeetCode 19.0, AtCoder 15.6, CF 11.1). Per-platform oracle strategy: - AtCoder: official public + hidden tests used directly (ground truth from the judge itself). - LeetCode: hidden tests unavailable -> generator-based input generation (Sec A.2): GPT-4-Turbo writes Python input generators from the problem spec via in-context learning — 22 random + 4 adversarial generators sampling small/medium/large sizes; capped at 100 inputs/problem. - Codeforces: long tests truncated on the site -> semi-automatically written test generators.

    Validation of generated tests (automated): generated inputs are executed against collected accepted (officially correct) solutions; an input is kept only if the correct programs handle it, and expected outputs come from those official-verdict-validated solutions. Judge-verdict grounding: the oracle output is produced by code the real judge already accepted.

    Scope discipline: problems that "accept multiple correct answers" are excluded outright (Sec 3.1) — sidesteps the special-judge problem rather than solving it.

    Contamination control (Sec 5.1): every problem carries a release date; evaluation windows sliced to post-cutoff months. Evidence: DeepSeek-Instruct-33B falls from ~60% to ~0% pass@1 on LeetCode problems released after its Sept 2023 cutoff; GPT-4o drops after Nov 2023; Codestral 36.5% -> 28.3% post-Feb 2024. Performance stays smooth on AtCoder, isolating LeetCode-specific contamination.

    Lifecycle: continuous — new contest problems scraped, tests generated/validated per release, leaderboard windows rolled forward. Code-execution subset used compile/run-time filters + manual inspection (~2,000 solutions -> 479 samples).

    3. BigCodeBench¶

    Paper: https://arxiv.org/html/2406.15877v4 ; HF blog https://github.com/huggingface/blog/blob/main/leaderboard-bigcodebench.md ; OpenReview https://openreview.net/forum?id=YrycTjllL0

    Three-stage pipeline: (1) Data synthesis: GPT-4 enriches ODEX/Stack Overflow seeds -> 4,718 samples. (2) Semi-automatic refactoring + test generation: 13 annotators (~100 tasks each) steer GPT-4 Code Interpreter with iterative execution feedback -> 1,223 valid tasks (~3,495 rejected). (3) Human curation -> final 1,140 tasks.

    Test adequacy mechanisms: - Branch coverage as explicit floor: average 99% branch coverage per task; 5.6 test cases/task (Table 1), all unittest-encapsulated, pytest-compatible. - Tests must "verify program behaviors" (behavior-style assertions, mocked external services, DB/directory fixtures) rather than bare I/O equality. - Determinism written into the curation rubric: tests must be "deterministic, asserting expected program behaviors based on the inputs"; humans specifically resolved "runtime issues due to the LLM-generated flaky tests" (GPT-4 truncating long file writes was a recurring flake source) (Sec 2.3). - Pre-evaluation probe: GPT-3.5-Turbo dry-runs every prompt; where it fails from ambiguity, annotators clarify docstrings without leaking implementation steps — an LLM used as ambiguity detector, not judge. - Cross-checking: 7 additional annotators; docstrings validated via doctest; automated execution in a GitHub Container Registry sandbox (fixed environment = reproducibility control). - Human solvability audit: 33 random tasks solved from scratch by 11 annotators; 97% (32/33) passed all tests — a measured human-pass calibration of oracle fairness.

    Annotators: 20 author-annotators over ~1 year, 75% with 5+ years Python. Lifecycle: all QA at construction; sandboxed automated scoring afterward.

    4. Mutation testing as benchmark QA¶

    • EvalPlus itself uses mutant-killing as one of three adequacy requirements for test-suite reduction — mutation analysis as construction-time QA criterion, not a task.
    • Direct adequacy audit of the benchmarks' own suites: Liu et al., "Evaluating the Test Adequacy of Benchmarks for LLMs on Code Generation" (JSEP 2025, https://onlinelibrary.wiley.com/doi/10.1002/smr.70034) mutation-scores HumanEval/MBPP/HumanEval+/MBPP+ suites: statement coverage looks fine (>99.16%) but branch coverage only 74.39% and mutation score 87.69%; mutation score degrades with cyclomatic complexity; augmentation lifts mutation score ~34.6%. Also finds EvalPlus-style LLM generation beats search-based Pynguin for strengthening benchmark suites. Transferable headline: coverage is a weak proxy; mutation score exposes the real holes.
    • UTBoost (https://arxiv.org/pdf/2506.09289) is the SWE-bench analogue of EvalPlus: GPT-4o localizes then generates augmenting tests, validated by intramorphic testing (gold-patched program vs candidate-patched program must agree on the new tests). Found insufficient tests in 7.7% of SWE-bench Lite and 5.2% of Verified instances; among leaderboard patches passing original tests in those instances, 28.4% (Lite) and 15.7% (Verified) were false passes; combined with parser fixes: 176 (Lite) / 169 (Verified) erroneous patches, changing 40.9% of Lite and 24.4% of Verified leaderboard entries' ranks. Human element: two authors manually adjudicated each detected discrepancy. Cost ~$1.60/instance.
    • Adjacent transferable work: mutation-guided regression-suite diagnosis (https://arxiv.org/html/2604.01518), SWE-Mutation (https://arxiv.org/html/2605.22175v1), replication showing coverage/mutation only partially predict effectiveness (https://arxiv.org/html/2607.22880v1). Meta's mutation-guided test generation in production, 73% engineer acceptance (https://www.researchgate.net/publication/394720083_Mutation-Guided_LLM-based_Test_Generation_at_Meta).

    5. Differential and multi-reference validation¶

    • AlphaCode / CodeContests (https://arxiv.org/pdf/2203.07814), the origin story: example-only tests gave a 30-62% false-positive rate; they mutated existing test inputs (bit flips, int ±, char swaps) and kept a mutated input only if 30 independent accepted solutions all produced the same output (N-version agreement as oracle), budget 10 CPU-hours or 200 tests/problem, cutting FP rate to ~4%.
    • CodeContests+ (https://arxiv.org/html/2506.05817v1): Generator agent (testlib-based, ~20 seeded commands: random/corner/adversarial/TLE inputs) + Validator agent (constraint checker, error-message feedback loop until all tests validate) + Checker agent (custom output checkers for multi-answer problems; built-ins for float tolerance, yes/no, full text). Graded against 1.72M labeled submissions via TPR (correct solutions pass) / TNR (wrong solutions fail): problems with TPR&TNR >= 0.9 roughly doubled (~5k -> ~10k); original CodeContests had >4,000 problems with TPR <= 0.1 (correct code failed the shipped tests) and only 67.1% of its own tests passed constraint validation. 11,690 problems; 25 (1x) / 98 (5x) tests avg.
    • AutoCode (https://arxiv.org/pdf/2510.12803): Validator-Generator-Checker with candidate selection (3 LLM-written validators judged on 40 valid/near-invalid inputs; 3 checkers judged on 40 correct/incorrect outputs). Verdict-consistency vs official Codeforces judges: 98.7% (FPR 1.3%, FNR 1.2%) on 720 recent problems; 91.1% on the 7,538-problem set vs HardTests 81.0%, TACO 80.7%, CodeContests+ 79.9%. Dual verification: reference std.cpp vs brute.cpp outputs must agree under the checker (filtered 27% of error-prone generated problems, correctness 86% -> 94%); interactors chosen to pass the reference while killing the most LLM-generated mutant solutions.
    • Property-based: benchmark-side PBT still nascent: Property-Generated Solver validates via invariants instead of I/O pairs (https://arxiv.org/html/2506.18315v1); PBT-Bench benchmarks agents ON PBT (https://arxiv.org/pdf/2605.15229); the oracle-automation survey warns of oracle leakage when judging LLM-written oracles on Defects4J (https://dl.acm.org/doi/10.1145/3715107). No major execution benchmark yet ships Hypothesis-style properties as its primary oracle; BigCodeBench's behavioral-assertion style is the closest mainstream approximation.
    • SWE-bench Verified (https://openai.com/index/introducing-swe-bench-verified/): 93 professional developers annotated 1,699 samples on 0-3 severity rubrics (underspecified issue; FAIL_TO_PASS tests that could unfairly reject valid solutions); 38.3% flagged for underspecified issues, 61.1% for unfair tests; 68.3% of SWE-bench filtered overall -> 500-instance set. Yet SWE-Bench+ (https://openreview.net/forum?id=R40rS2afQ3 , arXiv:2410.06992) still finds 22.6% solution leakage and 15.2% weak-test instances IN Verified; across original SWE-bench, 47.93% of "resolved" issues were plausible-but-wrong patches passing weak tests; filtering drops agent resolution roughly in half (Lite 42.1% -> 21.8% avg, Verified 51.7% -> 25.9% avg). Lesson: one human pass over oracles is not terminal; adversarial re-audits keep finding false passes.

    6. Determinism discipline¶

    • EvalPlus: runtime cap max(200ms, 4x ground-truth time) per test to absorb machine noise; float tolerance absolute 1e-6 unless problem-annotated; exact match elsewhere (https://arxiv.org/abs/2305.01210, Appendix).
    • BigCodeBench: determinism is a curation rubric item; flaky LLM-generated tests hand-repaired; external effects (network, DB, filesystem) mocked or fixture-managed; execution pinned to a containerized sandbox (https://arxiv.org/html/2406.15877v4).
    • TDD-Bench Verified (IBM): cleanest published rerun policy: golden solution executed against the suite 3 times in independent containers; instance kept only if pass/fail verdicts identical across all three runs (https://arxiv.org/html/2412.02883v1 , https://github.com/IBM/TDD-Bench-Verified).
    • SWE-bench Verified: shipped a containerized Docker harness specifically for reproducible evaluation, alongside the human screen for environment-dependent tests (https://openai.com/index/introducing-swe-bench-verified/).
    • LiveCodeBench: avoids nondeterministic oracles structurally by excluding multi-answer problems; competitive-judge ecosystems (CodeContests+, AutoCode) instead solve it with checkers plus testlib's platform-stable seeded RNG for reproducible generation (https://arxiv.org/html/2506.05817v1).
    • AlphaCode: the N=30 agreement vote doubles as a flake filter — any input where accepted solutions disagree (nondeterminism or under-specification) is discarded (https://arxiv.org/pdf/2203.07814).

    Cross-cutting synthesis¶

    1. Every audited benchmark leaked false passes at double-digit rates until adversarially tested: HumanEval up to ~29% pass@100 inflation; CodeContests 30-62% FPR; SWE-bench ~48% plausible-patch rate; even SWE-bench Verified 15.7-24% depending on auditor.
    2. The strongest oracle-validation primitive is agreement among independently-validated correct solutions: AlphaCode's 30-way vote, LiveCodeBench's accepted-solution grounding, AutoCode's std-vs-brute dual verification, EvalPlus's differential ground-truth check. Ground truth is itself under test everywhere — 11% of HumanEval references were wrong.
    3. Adequacy is measured, not assumed: mutation score + wrong-sample killing (EvalPlus), branch-coverage floors (BigCodeBench 99%), TPR/TNR against labeled solution corpora (CodeContests+), verdict consistency vs official judges (AutoCode 98.7%).
    4. Human effort concentrates at three points: precondition/contract writing, ambiguity adjudication, flake repair; generation and adequacy scoring are otherwise automated.
    5. QA never ends at release: UTBoost and SWE-Bench+ both re-audited already-"verified" benchmarks and moved leaderboards — argues for periodic mutation/differential re-audits as an operating discipline, not construction-only.
